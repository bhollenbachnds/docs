## Authentification

PADS4 Foundation utilise **l'authentification de session basée sur les cookies** — pas de jetons Bearer.

### 1. Se connecter

```bash
curl -c cookies.txt -X POST \
  'https://<your-server>/rdx/NDS.Services.Authentication/api/v1/Account/Logon' \
  -H 'Content-Type: application/json' \
  -d '{"Username":"Administrator","Password":"<password>","Domain":"pads"}'
```

**Corps de la réponse :**

```json
{
  "Claims": [
    {"Name": "userId",      "Value": "d4e5f6a7-b8c9-0d1e-2f3a-4b5c6d7e8f9a"},
    {"Name": "displayName", "Value": "Administrator"},
    {"Name": "email",       "Value": "admin@pads4.com"}
  ],
  "Code": 0,
  "Succeeded": true,
  "Message": null
}
```

Le serveur définit un `Set-Cookie` en-tête contenant le cookie de session. Le corps de la réponse est un tableau de **16 revendications d'identité** (ID utilisateur, nom d'affichage, e-mail, domaine, rôles, etc.) — ce n'est PAS un jeton à renvoyer.

### 2. Utiliser le cookie de session

```bash
# Reuse the saved cookie in all subsequent calls
curl -b cookies.txt 'https://<your-server>/rdx/NDS.Services.Cms/api/v1/cms/message'
```

**Dans Postman :** Après avoir exécuté la requête Logon, Postman stocke le cookie de session et l'inclut automatiquement dans les requêtes suivantes vers le même domaine.

**Dans fetch / navigateur :**

```js
fetch('/rdx/NDS.Services.Cms/api/v1/cms/message', { credentials: 'include' })
```

## Conventions REST PADS4

PADS4 Foundation utilise un **modèle REST non standard** qui diffère des API CRUD classiques :

| Opération            | REST conventionnel      | Modèle PADS4                              |
| -------------------- | ----------------------- | ----------------------------------------- |
| Lister / filtrer     | `GET /resource`         | `POST /resource` avec corps de filtre     |
| Créer                | `POST /resource`        | `POST /resource/store` avec `Id: null`    |
| Mettre à jour        | `PUT /resource/{id}`    | `POST /resource/store` avec `Id`          |
| Obtenir un élément   | `GET /resource/{id}`    | `GET /resource/{id}` ✓ standard           |
| Supprimer un élément | `DELETE /resource/{id}` | `DELETE /resource/{id}` ✓ standard        |
| Suppression en masse | N/A                     | `POST /resource/delete` avec tableau d'ID |

**Pourquoi POST pour lister ?** PADS4 transmet les paramètres de filtre/pagination dans le corps de la requête (objets complexes avec `PageIndex`, `PageSize`, filtres, tris). Cela évite les limites de longueur d'URL et la complexité de l'encodage URL pour les grands ensembles de filtres dans les chaînes de requête.

### Exemple de liste

```bash
curl -b cookies.txt -X POST 'https://<your-server>/rdx/NDS.Services.Cms/api/v1/cms/message' \
  -H 'Content-Type: application/json' \
  -d '{"PageIndex": 0, "PageSize": 20}'
```

### Exemple de création

```bash
curl -b cookies.txt -X POST 'https://<your-server>/rdx/NDS.Services.Cms/api/v1/cms/message/store' \
  -H 'Content-Type: application/json' \
  -d '{"MessageId": null, "Name": "Welcome Screen", "IsEnabled": true}'
```

## Enveloppe de réponse standard

Toutes les réponses de l'API PADS4 encapsulent leur charge utile dans une enveloppe standard :

```json
{
  "Data": { ... },
  "Code": "OK",
  "Succeeded": true,
  "Message": null
}
```

| Champ       | Type         | Description                                                  |
| ----------- | ------------ | ------------------------------------------------------------ |
| `Code`      | string       | `"OK"` en cas de succès, ou une chaîne de code d'erreur      |
| `Succeeded` | bool         | `true` en cas de succès                                      |
| `Message`   | string\|null | Message d'erreur lisible par l'humain, null en cas de succès |

## Points de terminaison d'infrastructure communs

Chaque microservice PADS4 expose ces points de terminaison quel que soit son domaine :

| Méthode | Chemin                                    | Description                                     |
| ------- | ----------------------------------------- | ----------------------------------------------- |
| GET     | `/api/v1/health`                          | Vérification de santé basique                   |
| GET     | `/api/v1/health/clean`                    | Vérification de santé approfondie               |
| GET     | `/api/v1/diagnostics/toggles`             | États des indicateurs de fonctionnalité         |
| GET     | `/api/v1/diagnostics/configuration`       | Dump de configuration active                    |
| GET     | `/api/v1/diagnostics/configurationex`     | Configuration étendue                           |
| GET     | `/api/v1/diagnostics/circuitbreakers`     | État du disjoncteur                             |
| POST    | `/api/v1/diagnostics/events`              | Interroger les événements de diagnostic         |
| GET     | `/migration`                              | État de la version de migration                 |
| GET     | `/version`                                | Chaîne de version du service                    |
| POST    | `/api/v1/Management/RequeueErrorMessages` | Remettre en file d'attente les messages échoués |
| POST    | `/api/v1/Management/PurgeErrorMessages`   | Purger les messages échoués                     |
